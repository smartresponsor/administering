= Runtime Composer and Lock Authority

Administering has one canonical runtime-composition responsibility: it validates operator runtime decisions against host Composer inventory and materializes accepted decisions into runtime lock files.

== Authority chain

The authority chain is deliberately short:

. Host Composer inventory is the source evidence for installed SmartResponsor components and Symfony bundles.
. Composer inventory defines the available capability boundary, not the enabled runtime set.
. The operator decides which available components are enabled or disabled for a given runtime environment.
. Administering validates the operator decision against Composer inventory.
. Administering materializes the accepted decision into host lock files.
. The host Kernel reads only the lock files during boot.

The host Kernel must not call Administering services during boot. Administering may generate, validate, and mutate the lock files, but the boot path remains a plain PHP file read.

== Composer inventory is not the enablement decision

Composer files answer whether a component can exist in the host application. They do not answer whether that component is currently enabled.

This distinction is required for development and production parity. A dev Composer inventory may contain many components while a local runtime lock keeps some of them disabled. Production may use a smaller Composer inventory and still requires an explicit runtime lock decision.

== Lock files

The host App owns the materialized lock files:

* `config/kernel/runtime_scope.lock.php`
* `config/kernel/runtime_scope.prod.lock.php`

The lock files carry runtime decisions such as:

* enabled bundle class strings;
* enabled scope tokens;
* enabled entity tokens;
* disabled component tokens;
* source Composer file evidence.

`APP_RUNTIME_SCOPE` and `APP_RUNTIME_ENTITY` are not the primary source of runtime truth in this model. They may remain only as legacy/fallback vocabulary until every host consumer reads the materialized lock files.

== Coupling rule

Administering must not import owner component namespaces such as `App\Vendoring`, `App\Billing`, `App\Cataloging`, or `App\Rolling`.

Administering may handle owner component class names only as string evidence read from Composer inventory, component catalog files, or runtime lock files. It must not use owner bundle classes, contracts, services, forms, or handlers as PHP types inside the standalone Administering package.
