= Administration Service Tool Index Canon

The Administering component uses a hybrid source model for EasyAdmin tool screens.

== Source of truth

`src/Service/<Direction>/*.php` is the source of truth for tool existence.
SQLite-backed Doctrine entities are projections used by EasyAdmin indexes and must not become a manually-authored tool registry.

A PHP file is a service tool only when all conditions are true:

* the file lives directly under `src/Service/<Direction>/`;
* its namespace is `App\Administering\Service\<Direction>`;
* its class short name follows `Administration<Direction><ToolSlug>Service`;
* `<Direction>` is exactly the direct folder name under `src/Service`;
* `<ToolSlug>` is not empty;
* `Service` is the class suffix.

Example:

[source,text]
----
src/Service/Managing/AdministrationManagingFieldAccessMutationApplyService.php
----

This becomes:

[source,text]
----
sectionKey: Managing
directionToken: Managing
toolSlug: FieldAccessMutationApply
toolKey: managing.field_access_mutation_apply
----

== SQLite projection

The synchronized EasyAdmin index entity is `AdministrationServiceToolRecord` stored in `administration_service_tool_record`.

The record stores identity and launch metadata only:

* section key;
* tool key;
* service class;
* source file;
* optional form type class;
* optional primary route;
* status/checksum/safe context.

Tool records are regenerated by the service-section anchor sync operation and are not the canonical source for tool existence.

== EasyAdmin behavior

EasyAdmin indexes read `AdministrationServiceToolRecord` records from SQLite.
The `Open tool` action opens the concrete tool surface, not the normal entity edit screen.

The tool form is resolved by strict direction-token convention:

[source,text]
----
App\Administering\Form\<Direction>\Administration<Direction><ToolSlug>FormType
App\Administering\Value\Form\<Direction>\Administration<Direction><ToolSlug>Data
----

The older fallback shape without the direction token is not considered by the filesystem catalog.

Execution remains reserved for operation/audit services. The form route is a foundation for controlled submit, review, operation run creation, and audit recording.

== Non-tool classes

Provider, recorder, queue, scanner, writer, DTO, value, definition, catalog, parser, and helper classes must not rely on `src/Service/<Direction>` placement for menu exposure.
If such classes remain in `src/Service`, the strict parser ignores them unless they satisfy the tool class convention.

== Wave: tool form submission boundary

A synchronized service-tool record is not a normal editable CRUD object. The EasyAdmin
row is an index/projection of a canonical PHP service file. The row action named
`Open tool` must open the resolved tool form and, on valid submission, create a
metadata-only `AdministrationOperationRun`.

The generic operation type for this boundary is:

[source,text]
----
administration.service_tool.launch
----

The operation context must contain safe metadata only:

* `toolKey`
* `sectionKey`
* `toolSlug`
* `serviceClass`
* `serviceFile`
* `formTypeClass`
* scalar/public form data after redaction

The form submission must not directly mutate Symfony configuration, service wiring,
routes, secrets, or framework package configuration. Concrete execution remains owned
by a tool-specific operation handler. Until such a handler exists, the generic runner
may mark the operation as skipped while preserving the audit trail and submitted safe
context.

Doctrine access for service-tool records must use the Doctrine manager assigned to
`AdministrationServiceToolRecord`, so the host can route Administering system state to
SQLite/system storage instead of user/business PostgreSQL storage.

== Wave: service-tool execution dispatch contract

Service-tool form submission now has an explicit execution boundary after the
operation run is persisted.

The form-open flow remains:

. `AdministrationServiceToolRecord` is read from SQLite/system storage.
. The tool form is resolved from the record/convention.
. A valid submit creates an `AdministrationOperationRun` with safe context only.
. Messenger dispatches the operation key.
. `AdministrationGovernanceOperationRunner` delegates
  `administration.service_tool.launch` to `AdministrationServiceToolExecutor`.

The executor does not execute a PHP service merely because it exists in
`src/Service/<Direction>`. A concrete service must also implement
`AdministrationServiceToolHandlerInterface` and therefore be present in the
`administering.service_tool_handler` tagged locator.

This creates two different statuses:

* indexed/openable tool: discovered from file/path/name/namespace convention;
* executable tool: discovered tool plus explicit handler contract.

If a submitted tool has no executable handler yet, the operation is safely
marked as skipped with the service class and required contract in safe context.
This is intentional. It prevents accidental execution of providers, catalogues,
recorders, or support classes that happen to live near tool services.

Canonical handler signature:

[source,php]
----
public function handleAdministrationServiceTool(
    AdministrationServiceToolInvocation $invocation
): AdministrationOperationExecutionResult;
----

`AdministrationServiceToolInvocation` carries only safe metadata and redacted
form data copied from the persisted operation run. Raw secrets, raw source file
contents, and unmanaged runtime objects are forbidden in this payload.

== Wave: first executable apply handlers

The first concrete executable handlers are the apply tools that already had
operation-safe service boundaries:

[source,text]
----
App\Administering\Service\Rolling\AdministrationRollingAclMutationApplyService
App\Administering\Service\Managing\AdministrationManagingFieldAccessMutationApplyService
----

Both services remain normal domain-facing Administering services through their
existing service interfaces. They additionally implement
`AdministrationServiceToolHandlerInterface`, which makes them executable from the
generic service-tool operation dispatch flow.

The submitted form field `requestKey` is read from the invocation's redacted
`formData`. The actor is resolved from `AdministrationCurrentUserContextProvider`
and falls back to `administering:service-tool` when the operation is executed
without an authenticated Symfony user context.

The handler result is converted to `AdministrationOperationExecutionResult` with
safe context only. The generic operation result therefore records:

* tool key;
* section key;
* tool slug;
* request key;
* result status;
* result success flag;
* result safe context.

This proves the end-to-end contract without turning every indexed service into an
executable tool. Future executable tools must opt in by implementing
`AdministrationServiceToolHandlerInterface`; openable/diagnostic tools may remain
indexed without an execution handler.

== Wave: invocation metadata and executable projection

The SQLite service-tool projection now records the distinction between a form
being mapped and a concrete executable handler being available.

`AdministrationServiceToolRecord` therefore carries:

* `formTypeClass` for the Symfony form opened by EasyAdmin;
* `formDataClass` for the expected DTO/value object behind the form;
* `executable` for the explicit handler-contract check.

The scanner continues to use the filesystem as the source of truth for tool
existence, but the synchronized SQLite record now exposes enough metadata for
EasyAdmin to distinguish these states:

* `indexed`: valid service-tool file, no mapped form yet;
* `form_ready`: valid service-tool file with a mapped form;
* `executable`: valid service-tool file, mapped form, and implementation of
  `AdministrationServiceToolHandlerInterface`.

This is intentionally stricter than the file convention alone. A correctly named
service may appear in the tool index and still not be executable until it opts in
through the handler contract.

`AdministrationServiceToolInvocation` also owns common safe form access helpers.
Concrete handlers should read submitted values through the invocation rather
than re-parsing raw arrays locally. This keeps operation handlers consistent and
prepares the next layer of typed tool-specific configuration forms without
making the generic executor aware of every form DTO.

== Service-tool convention audit

The EasyAdmin service-tool index intentionally skips every file under `src/Service/<Direction>` that does not prove it is a real openable tool.
A skipped file is not automatically an error at runtime, but it is architectural drift for the tool-surface folder because `src/Service/<Direction>` is reserved for tool candidates.

Use the audit command before a sync wave or cleanup wave:

[source,bash]
----
php bin/console administering:service-tools:convention-audit
php bin/console administering:service-tools:convention-audit Managing
php bin/console administering:service-tools:convention-audit --json
----

The audit reports files that should either be renamed to the canonical tool form or moved to a type-specific layer such as `src/Provider`, `src/Recorder`, `src/Catalog`, `src/Writer`, `src/Queue`, `src/Value`, `src/Form`, or a matching interface layer.

Canonical tool class shape:

[source,text]
----
src/Service/<Direction>/Administration<Direction><ToolSlug>Service.php
----

The `<ToolSlug>` is the non-empty substring between `Administration<Direction>` and `Service`.
`AdministrationManagingFieldAccessMutationApplyService` therefore produces `FieldAccessMutationApply` as the tool slug and `managing.field_access_mutation_apply` as the machine tool key.

== Refresh command

The canonical maintenance command for the service-tool projection is:

[source,bash]
----
php bin/console administering:service-tools:refresh-index
----

The command performs two steps in one owner-facing operation:

. synchronizes valid filesystem tools into `administration_service_tool_record`;
. audits `src/Service/<Direction>` for files that do not satisfy `Administration{Direction}{ToolSlug}Service`.

The command intentionally materializes only valid tools.  Helper, provider,
recorder, definition, or catalog files that remain under `src/Service` are
reported as convention drift and are not treated as menu tools.

For machine output use:

[source,bash]
----
php bin/console administering:service-tools:refresh-index --json
----

During transitional cleanup waves the command may be allowed to return success
while still printing violations:

[source,bash]
----
php bin/console administering:service-tools:refresh-index --allow-violations
----

`--allow-violations` must not be treated as canonical green readiness.  It is a
transitional operator convenience for applying waves while service-folder drift
is still being moved out of the tool surface.


== Convention remediation suggestions

The service-tool convention audit now emits a suggested action and suggested target path for every invalid file found under `src/Service/<Direction>`.

The suggestions are intentionally advisory. They do not move files automatically because service relocation can require namespace updates, service aliases, constructor type references, and documentation updates.

Suggested actions:

* `move_support_class_out_of_service_surface` means the file looks like a provider, catalog, recorder, writer, queue, scanner, runner, factory, auditor, or operator and should not live under the tool surface unless it is renamed into a real tool service.
* `rename_or_confirm_as_non_tool` means the file does not satisfy `Administration{Direction}{ToolSlug}Service` and must either be renamed as a true tool or moved to a non-tool layer.
* `fix_namespace_or_move_file` means the namespace and path disagree.
* `rename_tool_slug_to_uppercase_token` means the tool slug between the direction token and `Service` is not a valid PascalCase token.

The command remains safe for the touched-file workflow:

[source,powershell]
----
php bin/console administering:service-tools:refresh-index --allow-violations
php bin/console administering:service-tools:convention-audit
php bin/console administering:service-tools:convention-audit --json
----

A future relocation wave may use these suggestions as a review checklist, but touched archives must still apply explicit files only and must not delete or overwrite the repository wholesale.

== Relocation plan for non-tool service-surface files

`src/Service/<Direction>` is treated as a tool surface. Files in that surface are indexed as tools only when they satisfy the strict `Administration{Direction}{ToolSlug}Service` convention and the expected namespace/path relationship.

The command below builds a non-destructive relocation plan for files that are present under `src/Service/<Direction>` but should probably live in type-identifiable layers such as `src/Provider`, `src/Catalog`, `src/Recorder`, `src/Writer`, `src/Queue`, `src/Scanner`, `src/Runner`, `src/Factory`, `src/Auditor`, or `src/Operator`:

[source,bash]
----
php bin/console administering:service-tools:relocation-plan
php bin/console administering:service-tools:relocation-plan --json
php bin/console administering:service-tools:relocation-plan --write-json=delivery/patches/administering_service_tool_relocation_plan.json
----

The relocation plan is intentionally advisory. It must not delete files, move files, or rewrite namespaces automatically. Each entry must be reviewed against constructor wiring, service aliases, imports, routes, and tests before any touched-file patch relocates a class.

== Relocation plan validation

Before a relocation plan is converted into a touched-file patch, validate it for path and namespace safety:

[source,bash]
----
php bin/console administering:service-tools:relocation-plan:validate
php bin/console administering:service-tools:relocation-plan:validate --json
php bin/console administering:service-tools:relocation-plan:validate --write-json=delivery/patches/administering_service_tool_relocation_plan_validation.json
----

The validator is conservative and non-destructive. It reports conflicts such as:

* missing source files;
* missing target paths;
* duplicate target paths;
* target files that already exist;
* target paths equal to source paths;
* missing inferred target namespaces;
* any relocation entry that claims automatic moves are allowed.

A validation pass does not approve automatic relocation. It only confirms that the advisory plan has no obvious path/namespace conflicts before an owner-reviewed touched-file patch is created.

During transitional waves, operators may request a successful process exit while still writing the report:

[source,bash]
----
php bin/console administering:service-tools:relocation-plan:validate --allow-issues
----

`--allow-issues` is not a readiness signal. It is only a workflow convenience while the service-folder cleanup is still in progress.

== Relocation patch plan

After the advisory relocation plan and validation pass are available, the next safe step is to prepare a touched-archive relocation patch plan:

[source,bash]
----
php bin/console administering:service-tools:relocation-patch-plan
php bin/console administering:service-tools:relocation-patch-plan --json
php bin/console administering:service-tools:relocation-patch-plan --write-json=delivery/patches/administering_service_tool_relocation_patch_plan.json
php bin/console administering:service-tools:relocation-patch-plan --write-deleted-paths=delivery/patches/administering_service_tool_relocation_patch_deleted_paths.txt
----

The patch-plan command is also non-destructive. It separates relocation candidates into:

* `patchableEntries`, where source path exists, target path is known, target namespace is known, and no blocking validation error was found;
* `blockedEntries`, where a path/namespace conflict or missing metadata requires owner review first;
* `manualDeleteAfterPatchPaths`, which must only be used after a reviewed touched-file relocation patch has added the new target files and local syntax/autowiring checks pass.

The command must not be used as an automatic mover. It only prepares machine-readable delivery metadata for a future explicit touched-file patch.

== Connected provider relocation wave

Connected report providers are provider/read-model surfaces, not executable service tools. They are therefore relocated out of `src/Service/Connected` into `src/Provider/Connected` while preserving their existing `ServiceInterface\Connected` contracts and EasyAdmin surface controllers.

This keeps `src/Service/<Direction>` reserved for tool candidates following `Administration{Direction}{ToolSlug}Service` and prevents read-only providers from polluting the service-tool index.

== Accessing provider/recorder relocation wave

Accessing projection providers and request recorders are not service-tool launchers. They must not remain under `src/Service/Accessing` because the `Service/<Direction>` surface is reserved for filesystem-indexed tools and section sync services.

This wave moves Accessing read-model providers to `src/Provider/Accessing` and the Doctrine account-action request recorder to `src/Recorder/Accessing`. Existing service-interface aliases remain stable through `config/services.yaml`, so consumers continue depending on interfaces rather than concrete paths.

== Relocation batch: Audit recorders

Audit recorder implementations are not service-tool surface entries. They belong under `src/Recorder/Audit` and remain wired through `AdministrationAuditRecorderInterface`. This keeps `src/Service/Audit` from producing false tool-index candidates while preserving the existing audit contract.



=== Operation support relocation wave

Operation runner/provider/recorder/writer/queue classes are not service-tool candidates. They belong to type-identifiable layers (`src/Runner`, `src/Provider`, `src/Recorder`, `src/Writer`, `src/Queue`) and must not remain under `src/Service/Operation` when they are not openable tools. The `src/Service/<Direction>` surface remains reserved for valid `Administration{Direction}{ToolSlug}Service` tool candidates and intentional operation-facing services.

=== Rolling provider/recorder relocation wave

Rolling catalog/report providers and review recorders are support/read-model infrastructure, not service-tool launchers. They belong in type-identifiable layers (`src/Provider/Rolling` and `src/Recorder/Rolling`) while the executable ACL mutation apply tool remains in `src/Service/Rolling` as `AdministrationRollingAclMutationApplyService`.

This keeps Rolling's `src/Service` direction clean for actual tool candidates and prevents permission catalogs, report providers, and Doctrine recorders from appearing as false EasyAdmin service-tool records.

== Wave note: Managing provider relocation

Managing catalog/readiness providers are not executable service tools and must not remain under `src/Service/Managing`. They are type-identifiable provider classes and belong under `src/Provider/Managing`. The service-tool scanner must continue to treat only `Administration{Direction}{ToolSlug}Service` classes in `src/Service/<Direction>` as tool candidates.

== Wave note: platform provider/scanner/operator relocation

Configuration scanners, credential operators, environment status providers, and Symfony route catalog providers are support surfaces, not executable service-tool launchers. They belong in type-identifiable layers:

* `src/Scanner/Configuration` for filesystem configuration scanners;
* `src/Operator/Credential` for Symfony Secrets operators;
* `src/Provider/Environment` for runtime environment status providers;
* `src/Provider/Symfony` for Symfony route catalog providers.

Existing contracts remain under `ServiceInterface` for now and are wired through aliases in `config/services.yaml`. This wave keeps the public contracts stable while removing additional false-positive candidates from `src/Service/<Direction>`.


== Admin support relocation

The `src/Service/Admin` directory remains part of the service-tool surface and must not contain generic helper infrastructure. Admin support classes are sorted into type-identifiable layers instead:

* convention audit logic: `src/Auditor/Admin`;
* service-tool execution dispatch: `src/Executor/Admin`;
* operation-plan construction: `src/Factory/Admin`.

`src/Service/Admin` may keep only service/tool candidates that follow `Administration{Direction}{ToolSlug}Service`, such as `AdministrationAdminServiceToolRecordSyncService`.


== Accessing Sync Service Naming Correction

The Accessing section sync service is normalized to the service-tool surface naming convention:

[source,text]
----
src/Service/Accessing/AdministrationAccessingAccountRecordSyncService.php
----

The stale non-canonical path is removed after overlay by the touched-archive deletion manifest:

[source,text]
----
src/Service/Accessing/AdministrationAccessingAccountRecordSyncService.php
----

This keeps `src/Service/Accessing` aligned with the `Administration{Direction}{ToolSlug}Service` parser while preserving the existing section anchor synchronization responsibility.

== Operation service-surface normalization

The `Operation` service direction keeps only classes that satisfy the service-tool surface naming contract.
Infrastructure collaborators are relocated to type-identifiable layers:

* `AdministrationOperationRunFactory` lives under `src/Factory/Operation/`.
* `AdministrationOperationSubmitter` lives under `src/Submitter/Operation/`.
* the anchor sync operation service is named `AdministrationOperationServiceSectionAnchorSyncService` so its second token matches the `Operation` direction.

Old relocated paths are removed only after touched-archive overlay by using the deleted-paths manifest.


== Managing Form/Data Naming Canon

Managing tool forms and form data objects now include the same second token as the service direction:

* `AdministrationManaging{ToolSlug}FormType`
* `AdministrationManaging{ToolSlug}Data`

The older fallback shape `Administration{ToolSlug}FormType` / `Administration{ToolSlug}Data` is no longer used by the filesystem catalog. Forms for service tools must carry the direction token so filesystem tool indexing, form linkage, and operation invocation remain mechanically aligned.

== Wave note: strict form/data resolver

The filesystem service-tool catalog now resolves only canonical tool form and data classes:

[source,text]
----
App\Administering\Form\<Direction>\Administration<Direction><ToolSlug>FormType
App\Administering\Value\Form\<Direction>\Administration<Direction><ToolSlug>Data
----

This removes the transitional fallback to `Administration<ToolSlug>FormType` and `Administration<ToolSlug>Data`. A service tool may still be indexed without a form, but it will remain in `indexed` state instead of being incorrectly treated as `form_ready` through a stale fallback class.

== Sync service tools

Primary anchor synchronization services under `src/Service/<Direction>` are now executable service tools when they satisfy all three contracts:

* the strict service class naming convention `Administration{Direction}{ToolSlug}Service`;
* the strict form/data convention `Administration{Direction}{ToolSlug}FormType` and `Administration{Direction}{ToolSlug}Data`;
* `AdministrationServiceToolHandlerInterface`, either directly or through the section-anchor sync handler bridge.

This keeps the EasyAdmin index deterministic: sync services appear as normal tool records, the Open action resolves a canonical form, and submit dispatches through the same operation runner used by other service tools. The SQLite index remains a projection; the PHP service files remain the source of truth.


== Service-tool index readiness report

After `administering:service-tools:refresh-index` materializes filesystem tools into SQLite, the materialized EasyAdmin-facing state can be checked with:

[source,powershell]
----
php bin/console administering:service-tools:index-readiness
php bin/console administering:service-tools:index-readiness Managing
php bin/console administering:service-tools:index-readiness --json
php bin/console administering:service-tools:index-readiness --require-executable
----

The readiness command reads `administration_service_tool_record`; it does not rescan `src/Service` directly. This is intentional: the command reports what EasyAdmin will see from the SQLite projection after refresh-index.

Readiness states:

* `indexed`: canonical service file exists, but no canonical form is mapped yet.
* `form_ready`: canonical form is mapped, but the service is not executable through `AdministrationServiceToolHandlerInterface` yet.
* `executable`: canonical form/data are mapped and the service implements the executable handler contract.

This keeps the governance distinction explicit: a file can be discoverable and visible before it is safe to execute from EasyAdmin.

== EasyAdmin left-menu projection

The Administering left menu must not enumerate arbitrary controller routes or custom Twig screens.
It is built from the materialized SQLite service-tool index through `AdministrationServiceToolMenuSectionProviderInterface`.

Menu section identity remains aligned with `src/Service/<Direction>` and the static section catalog still owns icons and permissions.
Runtime counts and readiness are read from `administration_service_section_record` and `administration_service_tool_record` after `administering:service-tools:refresh-index`.

If the SQLite schema is not available yet, the menu provider falls back to the static filesystem catalog so the dashboard can still boot during initial installation.
After schema update and refresh-index, menu labels include the indexed visible/enabled tool count, for example `Managing (6)`.

The menu item target remains the stock EasyAdmin CRUD index for `AdministrationServiceToolRecord`, filtered by `sectionKey`.
This preserves the no-custom-template rule for normal tool indexes while still letting each row expose an `Open tool` action for the tool-specific form.

== Wave note: section menu links target CRUD index

Section entries in the left EasyAdmin menu now generate URLs for the stock `AdministrationServiceToolRecordCrudController` index with a `sectionKey` filter.
The menu builder no longer links section entries to the transitional `administration_service_section_tools` custom route.

[source,text]
----
menu section -> EasyAdmin CRUD index -> administration_service_tool_record filtered by sectionKey
----

The custom tool-open route remains reserved for opening a concrete tool form from a row-level `Open tool` action.
Normal section browsing is therefore entity-index based and remains compatible with EasyAdmin sorting, filtering, actions, and read-only CRUD behavior.


== Open action readiness gate

The stock EasyAdmin service-tool index must not expose `Open tool` for every materialized row.
A row is openable only when the synchronized SQLite projection says the tool is enabled, visible, and has a canonical FormType mapping.

The materialized record now exposes three separate readiness checks:

* `hasFormType()` — a canonical `Administration{Direction}{ToolSlug}FormType` exists.
* `isOpenable()` — the row is enabled, visible, and form-backed.
* `isRunnable()` — the row is openable and the service implements the executable handler contract.

This keeps three states distinct:

* indexed filesystem tool;
* form-backed/openable tool;
* executable/runnable operation tool.

EasyAdmin menu sections still point to the stock CRUD index.
The row-level `Open tool` action is displayed only for openable rows and routes to the operation form.


== Wave note: refresh-index preserves runtime row flags

`AdministrationServiceToolRecord` remains a materialized SQLite projection of filesystem tools, not the canonical source of tool existence. However, not every field in the projection has the same ownership.

On refresh, identity fields are always regenerated from PHP service files:

* section key;
* direction token;
* tool slug/key;
* service class/path;
* canonical form/data mappings;
* executable handler status;
* checksum and safe scanner context.

Runtime row-control fields are preserved by `toolKey` when a previous record already exists:

* `enabled`;
* `visible`;
* `position`.

This prevents `administering:service-tools:refresh-index` from wiping owner/admin runtime choices while still keeping service-file identity authoritative. If a tool file is renamed and its `toolKey` changes, it is treated as a new tool and receives default runtime flags.


== Runtime controls

The materialized tool record stores a small runtime-control layer: `enabled`, `visible`, and `position`.
These values are owned by SQLite/system storage and must be preserved across filesystem refreshes when the `toolKey` remains stable.

The command below updates those runtime controls without changing filesystem identity fields such as class name, file path, checksum, form mapping, or executable status:

[source,bash]
----
php bin/console administering:service-tools:runtime-configure managing.field_access_mutation_apply --disable --hide --position=200
php bin/console administering:service-tools:runtime-configure managing.field_access_mutation_apply --enable --show --json
----

This keeps the governing rule explicit: PHP files define tool existence and identity, while SQLite records hold EasyAdmin projection controls.

== Wave note: EasyAdmin runtime-controls form

The service-tool CRUD index now exposes a dedicated `Runtime controls` action for each materialized tool row.
This action opens a small reviewed EasyAdmin form for the SQLite-owned runtime fields only:

* `enabled`;
* `visible`;
* `position`.

The form does not edit filesystem identity or scanner-owned metadata:

* section key;
* direction token;
* tool slug/key;
* service class/path;
* FormType/Data mapping;
* executable handler status;
* checksum;
* safe scanner context.

This preserves the canonical split:

[source,text]
----
PHP service file -> tool identity and executable/form conventions
SQLite record    -> EasyAdmin projection and runtime controls
----

The `Open tool` action remains the action for launching the concrete tool form.
The `Runtime controls` action is only for governing row visibility, enablement, and ordering in the materialized index.


== Runtime controls audit

Changing `enabled`, `visible`, or `position` is runtime configuration, not filesystem identity.
Both the EasyAdmin `Runtime controls` form and the `administering:service-tools:runtime-configure` command must write an audit event with action `administration.service_tool.runtime_controls.updated`.

The audit context records safe before/after values and the change source (`easyadmin` or `console`). It must not duplicate service code, form data payloads, secrets, credentials, or user/business data.

This preserves the separation:

* PHP files define whether a tool exists.
* SQLite tool records expose runtime controls.
* Runtime-control mutations are auditable governance events.


== Runtime display label override

The generated tool label remains derived from the filesystem service class name and
is part of the scanned identity projection. A separate SQLite runtime field,
`labelOverride`, may be used by EasyAdmin or the console runtime-configure command
to adjust the display label without changing the PHP service file, namespace,
FormType mapping, handler status, checksum, or source path.

`refresh-index` must preserve `labelOverride` by stable `toolKey` in the same way
it preserves `enabled`, `visible`, and `position`. If a tool is renamed and the
`toolKey` changes, the override intentionally does not follow automatically.

== Runtime controls export

SQLite-owned service-tool runtime controls may be exported as a machine-readable
snapshot without changing the filesystem source of truth. The export is intended
for review, backup, environment comparison, and later controlled import flows.

[source,bash]
----
php bin/console administering:service-tools:runtime-controls:export
php bin/console administering:service-tools:runtime-controls:export Managing
php bin/console administering:service-tools:runtime-controls:export --json
php bin/console administering:service-tools:runtime-controls:export --write-json=delivery/patches/administering_service_tool_runtime_controls_export.json
----

The export includes runtime-owned values such as `enabled`, `visible`, `position`,
and `labelOverride`, plus read-only identity context such as `toolKey`,
`sectionKey`, `serviceClass`, and `checksum` for human review. The identity
context must not be treated as editable configuration: PHP service files remain
the source of truth for tool existence, naming, form mapping, and executable
handler status.

== Wave note: Runtime controls import

Runtime controls now have a reviewed import path that complements the read-only export command.

[source,bash]
----
php bin/console administering:service-tools:runtime-controls:export --write-json=delivery/patches/administering_service_tool_runtime_controls_export.json
php bin/console administering:service-tools:runtime-controls:import delivery/patches/administering_service_tool_runtime_controls_export.json --dry-run
php bin/console administering:service-tools:runtime-controls:import delivery/patches/administering_service_tool_runtime_controls_export.json
----

The import command may update only SQLite-owned runtime controls: `enabled`, `visible`, `position`, and `labelOverride`.
It must not update filesystem-derived identity fields such as `toolKey`, `serviceClass`, `serviceFile`, `formTypeClass`, `formDataClass`, `checksum`, or executable status.
Missing tool keys fail the import by default; use `--allow-missing` only when applying a reviewed export across branches where some tools are intentionally absent.
Every applied change writes the `administration.service_tool.runtime_controls.imported` audit event.

== Owner-side configuration tool provider transition

Administering now supports a transitional owner-side configuration tool provider contract.
This allows neighboring owner components to keep their own configuration tool classes, forms, form data objects, validation, and executable handlers while Administering remains the EasyAdmin projection/orchestration shell.

The preferred long-term ownership split is:

* owner component owns configuration semantics, owner-prefixed tool service classes, forms, data objects, definitions, and handlers;
* Administering owns discovery, SQLite materialized projection, EasyAdmin CRUD index, runtime controls, audit, readiness reports, and operation shell;
* the host/post-application owns environment, credentials, Symfony framework configuration, component enablement, and system SQLite storage.

Owner-side services should use the owner component prefix rather than an Administering prefix. Examples:

[source,php]
----
ManagingConfigurationFieldAccessMutationApplyService
AccessingConfigurationAccountRecordSyncService
RollingConfigurationAclMutationApplyService
----

Owner components expose tools by implementing:

[source,php]
----
App\Administering\ServiceInterface\Admin\AdministrationOwnerConfigurationToolProviderInterface
----

and returning:

[source,php]
----
App\Administering\Value\Admin\AdministrationOwnerConfigurationToolDefinition
----

Administering converts these owner definitions into the same `AdministrationServiceToolRecord` SQLite projection used by EasyAdmin. The external owner tool is therefore visible in the same stock EasyAdmin CRUD index, but the owner repository remains responsible for the real tool service, form type, data class, and handler.

During the transition, `AdministrationCompositeServiceToolCatalog` merges:

* internal Administering filesystem tools, as the legacy/internal source;
* owner-provided configuration tools, discovered through tagged owner providers.

This lets the ecosystem migrate gradually without breaking the current Administering index, runtime controls, or audit flow.

== Owner-side configuration tool validation

The transition to owner-side prefixes adds a validation boundary before owner-provided tools are materialized into the SQLite/EasyAdmin projection.

Owner repositories should expose configuration tools through `AdministrationOwnerConfigurationToolProviderInterface`, but the tool service itself must use the owner prefix, not the Administering prefix:

[source,text]
----
ManagingConfigurationFieldAccessMutationApplyService
AccessingConfigurationAccountRecordSyncService
RollingConfigurationAclMutationApplyService
----

Administering validates discovered owner definitions with:

[source,bash]
----
php bin/console administering:owner-configuration-tools:validate
php bin/console administering:owner-configuration-tools:validate Managing
php bin/console administering:owner-configuration-tools:validate --json
php bin/console administering:owner-configuration-tools:validate --write-json=delivery/patches/administering_owner_configuration_tool_validation.json
----

The validator checks the following before a tool is trusted as a stable projection source:

* provider component key/token matches the definition component key/token;
* component token is URL/key-safe lowercase snake text;
* tool slug is non-empty PascalCase;
* service class ends with the declared service short name;
* service short name follows `{Component}Configuration{ToolSlug}Service`;
* form type follows `{Component}Configuration{ToolSlug}FormType` when present;
* form data follows `{Component}Configuration{ToolSlug}Data` when present;
* executable tools expose at least a form type;
* generated `toolKey` is derived from `{componentToken}.{tool_slug}`.

Validation is intentionally separate from `refresh-index`. Discovery answers "what did owner providers expose?" Validation answers "is the exposed contract clean enough to trust?" Refresh answers "what is now materialized into SQLite for EasyAdmin?"

== Owner-side materialization guard

Owner-side discovery and validation are now connected to materialization through `AdministrationCompositeServiceToolCatalog`.

The composite catalog continues to merge two sources:

* Administering-internal filesystem tools;
* owner-provided configuration tools from tagged `AdministrationOwnerConfigurationToolProviderInterface` providers.

Before owner-provided definitions are returned to the shared service-tool sync flow, they are validated with `AdministrationOwnerConfigurationToolDefinitionValidatorInterface`.
Definitions with validation errors are skipped from SQLite materialization. Definitions with warnings can still be materialized, but should be reviewed and corrected in the owner repository.

[source,bash]

php bin/console administering:owner-configuration-tools:materialization-preview --json

----

The materialization preview answers the practical question: "Which owner tools will actually reach `administration_service_tool_record` on the next `refresh-index`?"

The expected transition workflow is:

[source,bash]
----
php bin/console administering:owner-configuration-tools:discover --allow-empty
php bin/console administering:owner-configuration-tools:validate --allow-empty --allow-warnings
php bin/console administering:owner-configuration-tools:materialization-preview --allow-empty --allow-rejected

php bin/console administering:service-tools:index-readiness
----

This keeps Administering thin: owner repositories own the tool service, form, data class, and handler; Administering only validates, materializes a SQLite projection, renders EasyAdmin, and records governance/audit state.

== Source ownership projection fields

The materialized `AdministrationServiceToolRecord` now stores source/provenance fields explicitly instead of hiding all provenance inside `safeContext`.

[source,text]
----
sourceOwnership      administering_internal | owner_component
ownerComponentKey    Managing | Accessing | Rolling | ...
ownerComponentToken  managing | accessing | rolling | ...
ownerProviderClass   provider FQCN that exposed the owner definition
ownerServiceClass    owner-side service FQCN
ownerSourceLabel     human-readable source label
----

These fields make the EasyAdmin index and readiness reports honest about where a tool came from:

* `administering_internal` means the tool is still owned by Administering's transitional internal surface.
* `owner_component` means the tool was discovered through an owner-side provider and materialized into SQLite only as an administrative projection.

The provenance fields do not make Administering the owner of external configuration semantics. Owner repositories still own their configuration service, form, data object, handler, and validation rules. Administering owns only discovery, validation, materialization, runtime controls, audit, and EasyAdmin rendering.

After applying this wave, update the SQLite schema and refresh the index:

[source,bash]
----
php bin/console doctrine:schema:update --em=system --force
php bin/console administering:owner-configuration-tools:materialization-preview --allow-empty --allow-rejected
php bin/console administering:service-tools:refresh-index --allow-violations
php bin/console administering:service-tools:index-readiness
----

== Owner-side open/execute guard

Owner-provided configuration tools are allowed to enter the Administering EasyAdmin surface only as projected records. Before a projected record can be opened as a form-backed tool, Administering validates the open boundary through `AdministrationServiceToolOpenGuardInterface`.

The guard enforces:

* `enabled=true`, `visible=true`, and a mapped `FormType` before a row can open.
* mapped form and form-data classes must exist.
* `sourceOwnership` must be either `administering_internal` or `owner_component`.
* owner-provided records must carry `ownerComponentKey`, `ownerComponentToken`, `ownerProviderClass`, and `ownerServiceClass`.
* owner-provided records must keep `ownerServiceClass` equal to the materialized `serviceClass`.
* owner-provided records must use owner-side form classes rather than Administering-owned form classes.

The same guard is also applied at persisted operation execution time through `AdministrationServiceToolInvocation`. This prevents a stale or manually edited SQLite projection from dispatching an owner-side operation without valid provenance metadata.

Administering remains the administrative shell: it renders the owner-provided form, submits the operation run, writes audit/status records, and delegates execution. The owner component remains responsible for the service/form/data/handler semantics.
