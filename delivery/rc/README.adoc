= Administering 3RC Proof Handoff
:toc:

== Purpose

This folder defines the owner-facing 3RC proof contract for the Administering + Rolling + Accessing connection.
The proof is runtime-oriented: it checks service wiring, Doctrine manager mappings, route presence, permission catalog consistency, synchronous operation lifecycle, and Messenger handler boundary behavior.

== Manifest

The machine-readable 3RC handoff manifest is:

[source,text]
----
delivery/rc/manifest.yaml
----

It defines the canonical proof commands, expected artifacts, pass criteria, bootstrap prerequisites, and known boundaries for the Administering + Rolling + Accessing RC gate.

== Primary proof command

Run from the host application or component checkout where the Administering, Rolling, and Accessing components are registered:

[source,powershell]
----
php bin/console administering:rc:proof --json
----

To persist a machine-readable proof artifact:

[source,powershell]
----
php bin/console administering:rc:proof `
  --operation-type="administration.configuration.scan" `
  --target-prefix="administering:rc-proof" `
  --output-file="delivery/rc/runtime-proof-results/administering-rc-proof.json" `
  --json
----

== Windows helper

A non-destructive helper is available at:

[source,text]
----
tools/runtime/capture-administering-rc-proof.ps1
----

Example:

[source,powershell]
----
powershell -ExecutionPolicy Bypass -File tools/runtime/capture-administering-rc-proof.ps1 `
  -ProjectRoot "D:\PhpstormProjects\www\Administering"
----

== Pass criteria

The proof is considered passing only when all sections report success:

* `administering:runtime:readiness`
* `administering:operation:lifecycle-proof`
* `administering:operation:messenger-boundary-proof`

The aggregate command must return exit code `0`, `ready=true`, and `status=ready`.

== Expected artifact

The expected default artifact paths are:

[source,text]
----
delivery/rc/runtime-proof-results/administering-rc-proof.json
delivery/rc/runtime-proof-results/administering-rc-proof-index.json
----

The proof JSON file is the canonical runtime result. The index JSON records the proof file path, SHA-256, manifest path, manifest SHA-256, operation type, target prefix, and capture timestamp for owner/watchdog intake.

== Bootstrap notes

Before running the proof on a fresh system database, the Rolling administration catalog should be synchronized:

[source,powershell]
----
php bin/console rolling:administration:catalog:sync --json
----

For a bootstrap Symfony user identifier:

[source,powershell]
----
php bin/console rolling:administration:catalog:sync `
  --bootstrap-user-identifier="admin@example.com" `
  --json
----

The bootstrap subject format must match the Administering subject provider, for example:

[source,text]
----
symfony:user:admin@example.com
accessing:account:123
----

== Machine-readable index

The Windows helper writes a proof index at:

[source,text]
----
delivery/rc/runtime-proof-results/administering-rc-proof-index.json
----

The index is intentionally small and stable so watchdog/owner tooling can validate the proof capture without parsing the full runtime proof first. It includes:

* component and RC stage
* manifest path and SHA-256
* proof result path and SHA-256
* operation type and target prefix
* UTC capture timestamp


== Known boundary

This proof invokes the Messenger handler in-process. It verifies the message payload and handler boundary, but it does not prove that an external async worker process is running.

== Artifact validation

After the aggregate proof has been captured, validate the handoff files with:

[source,powershell]
----
php bin/console administering:rc:proof-artifact:validate `
  --proof-file="delivery/rc/runtime-proof-results/administering-rc-proof.json" `
  --index-file="delivery/rc/runtime-proof-results/administering-rc-proof-index.json" `
  --manifest-file="delivery/rc/manifest.yaml" `
  --output-file="delivery/rc/runtime-proof-results/administering-rc-proof-validation.json" `
  --json
----

The validator checks that the proof JSON, index JSON, and RC manifest are present, parseable, internally consistent, and SHA-256 bound. The Windows helper runs this validation automatically and writes:

[source,text]
----
delivery/rc/runtime-proof-results/administering-rc-proof-validation.json
delivery/rc/runtime-proof-results/administering-rc-owner-review.json
----

== Owner-review verdict

After capture and artifact validation, build the final owner-review verdict with:

[source,powershell]
----
php bin/console administering:rc:owner-review `
  --proof-file="delivery/rc/runtime-proof-results/administering-rc-proof.json" `
  --index-file="delivery/rc/runtime-proof-results/administering-rc-proof-index.json" `
  --validation-file="delivery/rc/runtime-proof-results/administering-rc-proof-validation.json" `
  --manifest-file="delivery/rc/manifest.yaml" `
  --output-file="delivery/rc/runtime-proof-results/administering-rc-owner-review.json" `
  --json
----

The verdict is owner-facing and intentionally read-only. It does not rerun runtime proof or mutate system storage; it validates the captured proof, index, validation file, and manifest hashes. It also records SHA-256 hashes for the manifest, proof, index, and validation artifacts so the final seal can reject stale owner-review files. The Windows helper runs it automatically and writes:

[source,text]
----
delivery/rc/runtime-proof-results/administering-rc-owner-review.json
----

A passing owner-review artifact reports:

[source,json]
----
{
  "status": "ready_for_owner_review",
  "ready_for_owner_review": true,
  "artifacts": {
    "manifest_sha256": "...",
    "proof_sha256": "...",
    "index_sha256": "...",
    "validation_sha256": "..."
  }
}
----


== 3RC final seal

Wave65 adds a final read-only seal command on top of the owner-review verdict.
It does not rerun the proof and does not mutate Doctrine/system storage. It validates the captured proof, index, validation, owner-review, and manifest artifacts, including the owner-review artifact hashes, then writes the final owner/watchdog intake JSON.

[source,powershell]
----
php bin/console administering:rc:final-seal `
  --proof-file="delivery/rc/runtime-proof-results/administering-rc-proof.json" `
  --index-file="delivery/rc/runtime-proof-results/administering-rc-proof-index.json" `
  --validation-file="delivery/rc/runtime-proof-results/administering-rc-proof-validation.json" `
  --owner-review-file="delivery/rc/runtime-proof-results/administering-rc-owner-review.json" `
  --manifest-file="delivery/rc/manifest.yaml" `
  --output-file="delivery/rc/runtime-proof-results/administering-rc-final-seal.json" `
  --json
----

Successful seal status:

[source,json]
----
{
  "status": "sealed_3rc_candidate",
  "sealed_3rc_candidate": true
}
----

== Stale artifact guard

Wave68 strengthens the owner-review/final-seal boundary. The owner-review artifact now records SHA-256 hashes for the manifest, proof, index, and validation files. The final seal command verifies those hashes against the current files before it can report `sealed_3rc_candidate`.

This prevents a stale `administering-rc-owner-review.json` from being reused after the proof, index, validation, or manifest has changed.

* `delivery/rc/runtime-proof-results/administering-rc-final-seal-validation.json` - validates that the final seal still matches the current proof artifacts.

Wave89 keeps `composer rc:acceptance` as the terminal 3RC stop point and does not add another proof artifact. It hardens `administering:rc:contract:validate` so the static contract also checks the actual `composer rc:*` alias command strings.

The validator now fails before runtime proof if a required owner/watchdog artifact path is present in the manifest and Windows helper but missing from the composer aliases that create or consume the artifact. This protects the cross-platform `composer quality:rc-3rc` path from silently drifting away from the documented Windows helper path.

New static check coverage:

[source,text]
----
composer rc aliases mention every required 3RC artifact path
----

== Wave 90 post-3RC composer alias command guard

Wave90 keeps `composer rc:acceptance` as the terminal 3RC stop point and does not add another proof artifact. It hardens `administering:rc:contract:validate` so each required `composer rc:*` alias must invoke the expected Symfony console command name, not only mention the expected artifact paths.

New static check coverage:

[source,text]
----
composer rc aliases invoke expected Symfony console commands
* static_contract_validation coverage list is self-checked
----

This prevents a drift where an alias still references the right files but points to the wrong `administering:rc:*` command.



== Wave 91 post-3RC manifest composer-script guard

Wave91 keeps `composer rc:acceptance` as the terminal 3RC stop point and does not add another proof artifact. It hardens `administering:rc:contract:validate` so the manifest cannot silently list only part of the composer entry points.

New static check coverage:

[source,text]
----
manifest composer_scripts lists every required rc alias with the expected composer command
----

This prevents drift where `composer.json` contains a working alias but `delivery/rc/manifest.yaml` omits it, renames it, or points owner/watchdog documentation at the wrong composer command.

== Static contract alias coverage

The `administering:rc:contract:validate --json` guard also checks that `delivery/rc/manifest.yaml` contains a complete `composer_aliases` map for every required `rc:*` alias. This prevents the handoff manifest from documenting only a subset of the composer-only 3RC chain.
